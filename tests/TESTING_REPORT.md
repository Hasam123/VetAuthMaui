# Проверка VetAuthMaui — 30.10.2026

## Методика

Интеграционные запросы выполняются через HTTP к копии PHP API на отдельном
PHP-сервере. Для каждого запуска создаётся временная копия базы vet_clinic вместе
с таблицами, данными, ограничениями и триггерами. Запись в рабочую базу не производится.
После проверки сравниваются контрольные суммы строк всех семи рабочих таблиц.
Временная база и сервер удаляются после запуска.

Команды повторного запуска:

```powershell
C:\xampp\php\php.exe tests\clinic_journal.php
C:\xampp\php\php.exe tests\booking_time.php
dotnet build VetAuthMaui.csproj -f net10.0-windows10.0.19041.0 --no-restore -v quiet
dotnet build VetAuthMaui.csproj -f net10.0-android --no-restore -v quiet
```

Подробные результаты интеграционного запуска: `clinic_journal_results.json`.
Файл `workflow_checks.php` запускается только из изолированного тестового окружения.
Ненулевой код завершения интеграционных тестов ожидаем, пока перечисленные ошибки не исправлены.

## Успешные сценарии

- Регистрация с ФИО, телефоном, адресом и паролем; обязательные поля, повторный
  телефон, короткий пароль, ограничения длины и хеширование пароля.
- Вход клиента и ветеринара с правильным и неправильным паролем; пароли и их хеши
  не возвращаются в ответах входа; SQL-вставка в поле телефона не даёт войти.
- Создание, изменение и удаление питомца без приёмов; пол, вес с десятичной запятой,
  корректная дата вакцинации; запрет изменения и удаления по чужому телефону.
  Последняя проверка относится к проверке владельца по переданному телефону,
  а не подтверждает наличие полноценной серверной авторизации.
- Список, создание, изменение и удаление неиспользуемой услуги; категория и цена.
- Выбор активного ветеринара, отсутствие доступных интервалов у неактивного врача,
  расписание на пять дней, отказ для прошедшего времени и занятого интервала.
- Создание заявки, принятие ветеринаром, комментарии, отмена клиентом,
  освобождение времени, повторная запись и удаление заявки без медкарты.
- Обязательные группы медкарты: жалобы; один из диагнозов; лечение или процедуры.
  Первичный и повторный приём, выбор предыдущего посещения, вывод данных клиенту
  и врачу, ограничения даты заболевания и связей между приёмами.
- Откат транзакции при искусственно вызванной ошибке сохранения.
- Создание одной строки истории при завершении приёма, копирование медицинских
  данных, телефона, веса и остальных согласованных значений. Повторное сохранение
  не дублирует историю. Изменение и удаление источников не меняют сохранённую строку.
  Прямые UPDATE и DELETE истории блокируются триггерами.
- Статистика по статусам и количеству услуг совпадает с базой.

## Обнаруженные ошибки

| № | Проверка и фактическое поведение | Где исправлять |
|---|---|---|
| 1 | Удаление услуги, используемой в приёме: ошибка внешнего ключа не преобразуется в JSON с понятным отказом | api/services/delete.php |
| 2 | Изменение услуги с несуществующим id: сервер сообщает success=true | api/services/update.php |
| 3 | Создание питомца с датой вакцинации 2026-02-30 не отклоняется | api/pets/create.php |
| 4 | Изменение питомца с датой вакцинации 2026-02-30 возвращает некорректный для клиента ответ вместо JSON с отказом | api/pets/update.php |
| 5 | Статистика ветеринара доступна запросом без cookies и Authorization | api/admin/stats.php |
| 6 | Профиль клиента с медицинскими данными доступен без авторизации при передаче телефона | api/clients/profile.php |
| 7 | Комментарий приёма изменяется без авторизации при передаче id | api/appointments/update_admin_comment.php |

Пункты 5–7 подтверждают отсутствие серверной проверки доступа на проверенных
маршрутах. Это наиболее существенная проблема перед использованием вне учебной
среды. Проверка пароля при входе сама по себе не защищает последующие запросы:
нужны серверная сессия или токен и проверки владельца/ветеринара на маршрутах.
Это результаты проверки; исправления поведения API в рамках этого запуска не вносились.

## Границы проверки

Автоматические проверки API не заменяют проход по экранному интерфейсу.
Нажатия на кнопки, клавиатура, прокрутка, внешний вид на разных размерах экрана,
разрешения Android, установка на телефон, восстановление после потери сети и
работа приложения после сворачивания вручную в этом запуске не проверялись.
iOS и Mac Catalyst не собирались: для полноценной проверки этих платформ нужен Mac.
Повторное бронирование интервала проверялось последовательными запросами;
нагрузочное тестирование и конкурентные запросы отдельных серверных процессов
в этот прогон не входят.

По результатам нельзя утверждать, что приложение полностью безошибочно:
основные проверенные сценарии проходят, но семь проверок выявляют проблемы выше.
